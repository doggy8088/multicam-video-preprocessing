Section 02 · Skill Discovery & Operational Invariants

Agent 如何知道「何時」與「如何」操作音訊來源？

你問了一個非常關鍵的問題：這個工具如何讓 AI Agent 理解「該使用哪個 Skill、以及該怎麼對音訊來源進行操作」？ 答案不在某一段神奇的 AI 推理，而是透過 Agent Plugins 1.0 三層契約架構，把「意圖觸發」與「物理音訊演算法」徹底鎖定：

LAYER 1 · 探索層

plugin.json & SKILL.md

SKILL.md 的 YAML Frontmatter 明確宣告 name、description 與關鍵字（audio sync, loudness normalization, multicam, fcp7 xml）。當使用者輸入 /multicam-video-preprocessing 或自然語言提到「同步多機位、標準化響度」時，Agent 會依語意命中並載入該 Skill。

LAYER 2 · 行為邊界層

rules/AGENTS.md 執行鐵律

規定 Strict Read-Only Execution（嚴禁現場自己寫 Python 同步腳本） 與 Fail-Fast 原則。Agent 不能憑記憶自己拼湊 FFmpeg 指令或簡易音量比較，必須直接呼叫 scripts/multicam_pipeline.py 等官方入口，確保聲學演算法 100% 確定性。

LAYER 3 · 閘門工作流層

3-Stage Gated Runbook

SKILL.md 定義了嚴格的三階段閘門（Exit Gate 1/2/3）：每一階段必須驗證產出檔案存在且 > 0 bytes（例如 multicam_sync.json 與 *_synced.mp4），才允許進入下一階段。

設計啟示：把「該怎麼做」寫成確定性腳本，把「何時呼叫與判斷」交給 Skill + Gate
Agent 並不需要自己「理解」Mel 濾波器或 LUFS 數學公式；它透過 SKILL.md 知道：「只要遇到多機位音訊對齊、響度標準化、粗剪，就必須依序執行 Stage 1 → Gate 1 → Stage 2 → Gate 2 → Stage 3A/3B」，並透過 --strict-sync 與 --strict-edl 讓系統用數學門檻自我把關。

Section 04 · modules/audio_sync.py

音訊對齊核心原理：純 NumPy MFCC + 三階降級 + 次影格微調

多機位素材常面臨「不同麥克風增益差異」、「環境空調低頻噪音」、「長片記憶體爆表」三大難題。 audio_sync.py 完全不依賴 librosa 或 scipy，僅用 FFmpeg + 純 NumPy 就解決了這些問題：

1. 三道訊號預處理 (load_and_preprocess_audio)

  • 降取樣至 8 kHz 單聲道 PCM：大幅降低 97.7% 記憶體佔用，同時保留人聲關鍵頻段（≤ 4 kHz）。
  • Zero-mean 去直流偏移：raw - np.mean(raw) 消除硬體錄音底噪偏置。
  • 一階高通差分 (np.diff)：濾除冷氣/風扇低頻隆隆聲，強化語音子音與拍手打板的瞬態特徵。
  • 能量標準化 (Z-score)：除以標準差，消弭主機與副機的錄音音量差距。

2. 為什麼用 MFCC 而不是只用波形？

  • 兩台相機距離發話者遠近不同，相位與波形形狀會因空間殘響而扭曲，但梅爾倒譜特徵 (MFCC) 反映的是人耳對頻譜包絡的感知，抗殘響能力極強。
  • 計算 26-band Mel Filterbank 與 DCT-II 後，刻意丟棄 c0（能量係數），只取 c1..c12 並做 CMVN（倒譜均值與變異數正規化），讓比對完全不受音量大小影響。
  • 使用 1D FFT 加速互相關（O(N log N)），並用 f_ref_cache 快取參考機位的 FFT 結果供所有目標機位共用。

關鍵技術：次影格聲學微調 (refine_offset_subframe)
MFCC 的 hop_length = 128（在 8 kHz 下等於 16 ms 一幀），若只停在這裡，對齊誤差可能達到半幀影格。因此系統在取得粗略偏移 coarse_offset_sec 後，會利用累積平方和 (cumsum) 在共同重疊區間內找出能量最高的 5 秒片段，回到時域對原始高通波形在 ±256 samples (±32 ms) 範圍內做 np.correlate(..., mode="valid")，把精準度一舉推進到單一取樣點 1/8000 秒 = 0.125 ms！
Section 05 · modules/audio_normalizer.py

響度標準化：為何堅持 Two-Pass 線性增益 (linear=true)？

多機位現場常出現「主持人麥克風收音很飽滿，但來賓機位小聲很多」的情況。若直接使用 FFmpeg 的單階段 loudnorm，演算法無法預知整部片的動態範圍，只能啟用動態壓縮器 (Dynamic Mode)，導致安靜處底噪被拉大、說話時又被壓縮，產生明顯的「呼吸效應 (Pumping Artifact)」。

Pass 1（Null-Sink 聲學掃描）：快速解碼音軌至 -f null -，透過 print_format=json 取得全片真實聲學統計：input_i (整合響度)、input_lra (響度範圍)、input_tp (真實峰值)、input_thresh 與 target_offset。

Pass 2（純線性增益平移）：將量測結果回傳給 loudnorm 並加上 linear=true，對整條音軌套用恆定的線性增益推升至 -14.0 LUFS（YouTube / 廣播標準，LRA=11.0, TP=-1.5 dBTP），完全保留原始人聲的動態起伏與自然質感。

僅當 Pass 1 的 JSON 正則解析失敗時才會退回單階段動態模式。因為缺少全片先驗數據，FFmpeg 會即時進行 AGC 動態壓縮，容易把句間換氣與空調底噪拉高，不適合專業訪談母帶。

Section 06 · modules/video_segmenter.py

長片智慧分段：如何用音訊「找自然換氣點」？

當多機位網格影片超過 40 分鐘（2400 秒），單次送入 Gemini 推論容易觸發 Gateway 超時或思考預算不足。 但如果在講話講到一半時硬切，AI 就會失去前後文語意！video_segmenter.py 因此設計了一套音訊靜音感知分段器：

1800s – 2400s (30–40 分鐘)

1. 在每個理論等分點 nominal_cut 的 ±300 秒 視窗內，先執行 FFmpeg silencedetect=noise=-30dB:d=0.5，只掃描該局部視窗（不掃全片）。

2. 候選靜音區間的排序成本函數為：abs(mid - nominal_cut) - min(duration, 3.0) * 15.0 —— 優先挑選「靠近理想中點」且「停頓較長（最高獎勵 45 秒權重）」的自然換氣點。

3. 若現場背景音樂或吵雜導致找不到 -30dB 靜音，系統自動降級至 find_rms_energy_minimum()：以 8 kHz 單聲道、0.5 秒滑動視窗計算均方根能量 (RMS)，找出能量最低的波谷切分，並四捨五入至 0.1 秒以對齊 10 fps / 1s GOP 邊界。

Section 07 · generate_edl.py & edl_interview_template.md

當畫面合併成單一混音軌後，Gemini 3.8 Flash 如何剪輯？

在 Stage 1 最後產出的 multicam_merged_full.mp4 只有單一混音音軌（取自 0:a? 同步後的標準化參考音軌），搭配 10 fps、左上角印有 CAM1..CAMn 標籤的網格畫面。Stage 2 的提示詞工程設計了三個非常聰明的約束：

1. 跨模態聲線與嘴型校準

在「第零階段」過後，模型會建立 聲線特徵（音色、語調）↔ 網格畫面嘴型動作 ↔ 機位標籤 (CAM1..CAMn) 的對應表。只要某角色持續發話，鏡頭鎖定率達 90% 以上；1–2 秒的「嗯、對」短附和則會被過濾，避免零碎跳切。

2. 不對稱安全邊界 (Asymmetric Safety Margin)

針對片頭「5, 4, 3, 2, 1」或「Ready Action」倒數，Prompt 強制要求 寧可延後 0.2–0.5 秒緊貼正片首字起剪 (Late Cut)，也絕不提早切入半個倒數音節，並要求模型自我校驗 [Global_Start_Time, Global_Start_Time + 2.0s] 區間。

3. 動態思考預算 (calculate_dynamic_thinking_budget) 與 8 項 EDL 驗證

為了避免長影片推論超過 Vertex AI 的 300 秒閘道限制，generate_edl.py 會根據影片長度估算 Prefill 時間，在 1024 ～ 4096 tokens 之間動態分配 thinking_budget，並預設使用 MEDIA_RESOLUTION_LOW。產出 CSV 前後皆會通過 edl_validator.py 的 8 項結構檢查：

等級檢查代碼偵測內容
ERRORE_NO_ROWS / E_PARSE_TIMEEDL 無有效資料列，或時間戳格式無法解析
ERRORE_NEGATIVE_DURATION / E_NON_MONOTONIC結束時間 ≤ 開始時間，或時間軸倒退

Section 08 · Engineering Takeaways

你可以從這個專案學到的 5 個高價值工程設計

千萬不要讓 LLM 去算時間偏移量或自己切影片。這個專案把毫秒級同步 (audio_sync.py)、響度計算 (audio_normalizer.py) 與 NLE 時間軸轉換 (export_fcp7_xml.py) 全部交給確定性 Python + FFmpeg，只把「誰在說話、該切哪一機、哪裡是廢料」交給 Gemini 3.8 Flash。
在 audio_sync.py 中，作者自己寫了 mel_filterbank() 與 dct2_matrix()（合計不到 50 行），避開了 librosa / numba / llvmlite 在不同 macOS/Linux 環境的編譯地獄，同時讓記憶體驗證與測試變得極為輕量。
multicam_merged_full.mp4 刻意壓低為 10 fps、1200k、1s GOP (-g 10) 與 16 kHz 單聲道音訊。這不僅大幅節省多模態 Token 與 GCS 上傳頻寬，1s GOP 更讓長片需要切分時能直接用 -c copy 在秒級完成無損切割。
即使開啟 --strict-edl 並偵測到嚴重錯誤，generate_edl.py 依然會先把壞掉的 CSV 與驗證報告寫入磁碟才以 Exit Code 1 退出，方便工程師或 Agent 事後檢視 (Post-mortem)，同時用 finally 區塊保證雲端與本地暫存切片一定被清除。
透過 rules/AGENTS.md 明確禁止 Agent「自行撰寫臨時腳本」或「竄改 Skill 原始碼」，並強制要求 60 秒長任務回報進度與 Exit Gate 檔案檢查，這是目前建構生產級 AI Coding Skill 最穩健的範本之一。
Section 09 · FAQ

常見問題 FAQ

結論先講
同步不是拿兩條原始波形直接比對，而是在「特徵域」做互相關（Cross-Correlation，類似在兩段訊號間滑動尋找最吻合的位置）。不同機位的音量大小、頻響、底噪差異，是靠訊號預處理 + 倒譜正規化在比對前就先消掉；至於整體音量不一致的問題，則是同步完成後才由另一個模組做響度標準化。兩件事是分開處理的。

一、為什麼不能直接比對原始波形？

如果把兩台相機錄到的聲音波形直接疊在一起比對，往往會對不上，因為不同機位的錄音會遇到這些破壞波形相似度的因素：

干擾來源 白話解釋與對波形的影響
麥克風距離不同 離講者較遠的機位會錄到更多牆壁反射音（空間殘響），讓聲波的相位與形狀整個扭曲。
增益／錄音音量不同 兩台相機的收音靈敏度不同，波形振幅會整體放大或縮小。
空調、風扇低頻噪音 會在訊號上疊加持續的直流偏移（基準線飄移）與低頻隆隆聲。
各機頻響曲線不同 不同麥克風對高、中、低音的敏感度不同，導致頻譜輪廓（包絡）長得不一樣。

因此系統改用 MFCC（梅爾倒譜特徵）：它不看細碎的原始波形上下震盪，而是抽取「人耳對聲音頻譜輪廓的感知特徵」（例如母音、子音的音色結構），對空間殘響與音量增益差異的抗性極強。

二、比對前的四道預處理（load_and_preprocess_audio）

在計算 MFCC 之前，程式會依序對音訊做四步清理，每一步都對應一種干擾：

  1. 降取樣至 8 kHz 單聲道 PCM — 減少 97.7% 記憶體用量，同時完整保留人聲最關鍵的頻段（≤ 4 kHz）。
  2. Zero-mean 去直流偏移（raw - np.mean(raw)） — 把整段訊號的平均值歸零，消除硬體電路或環境帶來的基準線偏移。
  3. 一階高通差分（np.diff） — 計算相鄰取樣點的差值，等於濾掉緩慢變化的冷氣／風扇低頻噪音，同時放大語音子音與「拍手打板」這類瞬間變化的特徵（這正是時間對齊最準確的錨點）。
  4. Z-score 能量標準化（除以標準差） — 把訊號振幅拉到相同尺度，這一步就直接消掉了兩台相機的錄音音量差距。

三、MFCC 特徵的「音量免疫」設計

  • 計算 26-band Mel Filterbank → 離散餘弦轉換（DCT-II）。
  • 刻意丟棄 c0（能量係數），只取 c1..c12。
  • 再做 CMVN（倒譜均值與變異數正規化），消除各機位麥克風的固定音色偏差。
關鍵設計：為什麼錄音品質不同也能對齊？
c0 代表的就是這段聲音的「整體響度」資訊；丟掉 c0 再加上 CMVN 之後，比對結果在數學上就完全不受音量大小影響。 這就是為什麼兩台設備音量與收音品質不同，依然能精準對齊的核心原因。

四、實際怎麼找出時間偏移量？

  1. 3-Tier 階梯掃描：先用 120 秒片段快速估算（Tier 1: Fast）→ 若信心度不足再擴大為全長（Tier 2: Full）→ 最後才動用原始解析度（Tier 3: Raw），逐級精修，避免長影片一次吃爆記憶體。
  2. FFT 加速互相關：透過 1D 快速傅立葉轉換（FFT）把互相關計算壓到 O(N log N)，並快取參考機位的 FFT 結果（f_ref_cache）讓所有目標機位共用。
  3. 次影格微調（refine_offset_subframe）：MFCC 的 hop_length = 128（在 8 kHz 下每幀約 16 ms），這對影音剪輯還不夠細，誤差可能達半幀。因此取得粗略偏移後，系統會用累積平方和（cumsum）找出全片能量最高、人聲最清晰的 5 秒片段，回到時域對原始高通波形在 ±256 samples（±32 ms） 範圍內做 np.correlate(..., mode="valid")，把精度推進到單一取樣點 1/8000 秒 = 0.125 ms。
  4. 信心度評估：以互相關峰值的 Z-Score 判定可靠性（本頁模擬器中以 Z ≥ 12.0 作為高信心門檻）；若信心不足，會自動觸發下一層級的掃描。

五、那「聲音大小不一樣」的問題呢？

這不歸同步階段處理，而是在對齊完成後，由 audio_normalizer.py 解決：採用 Two-Pass 線性增益（linear=true） 將所有機位統一標準化到 -14.0 LUFS（LRA = 11.0、TP = -1.5 dBTP）。

  • Pass 1（量測）：透過 FFmpeg Null-Sink 空跑掃描，取得全片真實聲學統計值（input_i、input_lra、input_tp 等）。
  • Pass 2（套用）：套用恆定線性增益把整軌音量平移到目標響度，完整保留人聲強弱動態。
  • 為什麼不用單階段動態 loudnorm？ 單階段動態壓縮會在安靜片段把環境底噪拉大、講話時又壓縮音量，產生不自然的「呼吸效應（Pumping Artifact）」。

流程總覽

兩段不同機位音訊
  → 8kHz 降取樣 / Zero-mean / np.diff / Z-score（消除音量・底噪差）
  → MFCC（丟 c0 + CMVN，消除增益・頻響差）
  → 3-Tier FFT 互相關（找粗略偏移）
  → 時域次影格微調（精度 0.125 ms）
  → 各機位切齊、輸出 *_synced.mp4
  → Two-Pass 線性 loudnorm 統一到 -14 LUFS（解決音量不一致）

一句話總結：音量與錄音品質的差異在「特徵正規化」階段被數學上中和掉，所以不影響對齊；對齊完成後再用線性增益把響度統一，兩者各司其職、互不干擾。
